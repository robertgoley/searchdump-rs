# 1.1-10: searchdump-multi small-heap data defaults

Item from `main` 13c0725 (FEATURES-TODO): `searchdump-multi` dumps got HTTP 429 or ran a small-heap
bitnamilegacy Elasticsearch out of memory, because `DATA_FLAGS` gave every data run `--limit=5000` and
`--maxResponseMb=0`. Owner go-ahead 2026-11-14 (t95u). Committed on `release/1.1` only.

## Setup (2026-11-14, box, isolated podman store)

- Engines from `scripts/it/up.sh elasticsearch-plain` (single node, bitnami env conventions or the
  official image), heap set with `ES_HEAP`: bitnamilegacy 7.10.2 (OSS, CMS GC), bitnamilegacy
  8.6.1-debian-11-r0, official 8.19.23, bitnamilegacy 9.1.2-debian-12-r0.
- Data, one primary shard, no replicas, `dynamic: false`:
  - `pmc`: 20,000 PMC articles (~22 KB of JSON each, ~12 KB stored; 217-239 MB on disk);
  - `fat`: 3,000 documents of 40-120 KB random base64 (~80 KB each; 232 MB on disk).
- `searchdump-multi --input=$URL --output=DIR --match='^IX$'` with the default data flags, built from
  `release/1.1` (dbf8fb7 code; then this change). Scripts: `/workspace/l810-env/l1110b/{repro,final}.sh`
  (box only).

With `-- --limit=1000` on the same data: 7.10.2 and 8.6.1 at 256m dump both indices (pmc 7.5 / 7.1 s,
fat 6.4 / 6.7 s); `--limit=500` and `--limit=100` also pass on 7.10.2 `fat`. Wherever the node
survived, `_nodes/stats` showed `open_contexts` 0 after the run, so children already clear their
scroll; no change was needed there.

**Load side** (found while testing the fix): `searchdump-multi --direction load` of the `pmc` dump with
5000-document bulks (~105 MB) gets HTTP 429 `es_rejected_execution_exception`
(`coordinating_operation_bytes=105412441 > max_coordinating_and_primary_bytes=103795916`, i.e.
`indexing_pressure` = 10 % of a **1 GB** heap) through every retry. At 256m even 1000-document bulks
get HTTP 429 `circuit_breaking_exception` (pmc and fat). With `--maxBulkBytes=16mb` both load (fat 6.0 s,
pmc 8.6 s).

## Change

`src/bin/searchdump-multi.rs`:

- `DATA_FLAGS`: `--limit=1000` (was 5000), `--maxBulkBytes=16mb` (new; searchdump's default is 100 MB),
  `--maxResponseMb=0` removed, so searchdump's 256 MB response cap applies.
- Dump data runs: when the user gave no `--limit` (and not `--noDefaultDataFlags`), `GET /<index>/_stats/docs,store`
  gives the average stored bytes per primary document, and `page_limit_for` lowers the page to about
  16 MB stored (`PAGE_STORE_BUDGET`), at least 1, at most 1000, with a note:
  `note: fat: documents average 80 KB stored; dumping 206 per page instead of 1000 (give -- --limit=N to choose)`.
- Not done: halving the page on HTTP 429 inside searchdump. A node that dies from `OutOfMemoryError`
  sends no 429, so only a smaller first page protects it; adaptive retry remains a follow-up.
