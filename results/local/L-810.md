## Finding (fixed here): 413 said nothing
Elasticsearch answers an oversized request with HTTP 413 and an empty body; the error read
`Elasticsearch bulk failed with HTTP 413: ` and nothing else. It now adds: the request is larger than the cluster
accepts (`http.max_content_length`, 100mb by default), lower `--maxBulkBytes` below it, and a single document
above the limit cannot be indexed until the setting is raised. Exit code stays 1 (permanent, not retried).
Test: chaos `l810_payload_too_large_names_the_limit`. The 413/limit wording is marked for lead review (TASKS-LOCAL).

## Observations (not changed)
- **Tool memory per very large document is about 5.3x its size:** restoring the single 90 MB document peaks at
  ~500 MB, 110 MB with `--maxDocMb 0` at ~567 MB, and two 60 MB documents at ~518 MB. The README estimate
  (`(bufferSize + slices + concurrency) x limit x avg_doc_size x ~3 + ~15 MB`) assumes full batches of average
  documents, so with `--limit 100` it over-estimates these runs overall, but the per-document factor is
  above 3 (the read buffer, the parsed/encoded copy and the request body coexist). Worth a lead look before
  the formula is final; the huge restore (316 MB in one 60-document batch) peaked at ~746 MB (2.4x).
- ES 7.17 with a 2 GB heap handled the 90 MB document; heap use was ~1.95 of 2 GB at the end of the run, so
  2 GB is the floor for this case (the spec's "move it to B if it OOMs" did not trigger).
