## 1. Root cause

**The RC slowdown is not reproducible and is not caused by 1.1-10.** The perf suite's multi command is

    searchdump-multi --direction=dump ... --parallel=P --noDefaultDataFlags ... -- --limit=2000 --concurrency=1

`--noDefaultDataFlags` plus an explicit `--limit` means neither the 1.1-10 per-index `_stats/docs,store` probe
(`Cluster::avg_doc_bytes` runs only when the default `--limit=1000` is in the child flags) nor the smaller
pages ever run in the suite. Plan hypotheses 1 (probe) and 2 (5x more pages) therefore cannot explain the RC
numbers; the suite runs the same child flags as beta1. The remaining explanation is hypothesis 3 (box or engine
noise: a VM stall, or engine state after the preceding restore cases). The es710-secure p8 series in the RC
(warm-up 0.372 s, then 2.446 / 1.545 / 1.046 s, falling) matches a transient stall, not a deterministic cost.

## 3. Consequences for 1.2

- Section 4.3 "probe once in the parent" is a **cleanup**, not the fix for the suite numbers (L2-005 does it:
  one `_stats?level=indices` call for all indices).
- The real cost of 1.1-10 is page size on healthy clusters; `--serverLimits=auto` (5000-document pages when the
  heap allows) addresses it.
- 1.2-1g perf: the suite runs `--noDefaultDataFlags`, which implies `--serverLimits=off`, so suite multi cases
  measure the 1.1.0 child flags; `auto` is measured separately (L2-008).

## 5. Automax (design only, not implemented)
