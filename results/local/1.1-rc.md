# 1.1.0 RC: 16-engine L0 perf suite on grokbox (L-823)

Run 2026-11-15 00:00 ET to 2026-11-16 10:56 ET, `release/1.1` code (0d7d518 / a76635b code), isolated `l810-podman` store.
Results were added after the `v1.1.0` tag (main 47a73cc era); no code change, no rerun. Full tables:
[`scripts/perf/results/v1.1.0-rc-L0.md`](../../scripts/perf/results/v1.1.0-rc-L0.md); machine-readable comparison: `1.1-rc.json`.

## Result
- 16 engines, 592 case results: **575 PASS, 1 FAIL**, 16 skipped/not-run.
- 15 engines passed with rc=0. `elasticsearch8-plain` (ES 8.6.1) ended rc=1 with one failed case: `multi-restore-p8`.
- Median rc/beta1 searchdump wall time: **0.89** over 575 cells (faster is below 1). Node comparison: searchdump faster, median 2.31x over 366 Node-compared cases.

## Known failure: ES 8.6 plain multi-restore-p8
`elasticsearch8-plain` `multi-restore-p8` (rep 0): 5 of 16 children exited 1 with "target index ... was deleted during the restore and re-created".
The same case passed on `elasticsearch8-secure` (same ES 8.6.1) and on every other engine. Analysis: `project/plan/REVIEW-1.3.md`, item 1.3-R1.
Not fixed in 1.1.0 (code frozen).

## Harness issues (not 1.1.0 code)
- The box pauses between sessions, so engines only progressed while a session was active (hourly gaps, long wall times; per-engine run time is not comparable).
- After a resume, podman lost track of running engine containers (es8-secure, es819-plain, es819-secure servers kept running and the driver reaper missed them); they were stopped by PID. Also the RAM guard refused os2-plain several times (fast failures) before it ran. Harness fix belongs to 1.2.

## Findings
- Overall faster than beta1 (0.89). es710 slice cap (1.1-4a): dump-scroll-s2 2.111 -> 0.858 s plain, 2.211 -> 0.975 s secure.
- Slowest engine: os3-secure (1.16, 22 cells slower >10%), mostly dump cells (dump-scroll-s8 0.403 -> 1.531 s, dump-edge 2.01 -> 7.383 s); os2-secure 1.03.
- Multi p4/p8 are slower on several engines (1.1-10 smaller pages/bulks; expected; e.g. es819-plain multi-restore-p8 1.417 -> 4.981 s, es710-secure multi-dump-p8 0.404 -> 1.545 s, falling series 2.446/1.545/1.046 s so not deterministic). This belongs to the 1.2 plan (1.2-1a found the multi slowdown not reproducible).
- Other slow cells (>25%, wall >= 0.5 s) are listed below; short cells are noisy and the run overlapped with pauses. dump-edge is slower on several secure/OpenSearch engines.
- Overlap note: es710-plain overlapped about 3 minutes with check-clean-tree tests; not rerun.
