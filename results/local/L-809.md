**Baseline (LOAD-014 "meta types finish in under N minutes").** Dump of all 300 indices: mapping 0.03 s,
settings 0.03 s, index 0.04 s, alias 0.02 s. Restore: settings 10.9 s and mapping 5.1 s (one request per
index), index 10.5 s, alias 0.05 s (one atomic call). Data: dump 30,000 docs 1.3 s, restore about 1 s. The
script fails any meta run above 300 s; on this box every meta type is under 11 s, so N = 1 minute is a
comfortable bound for 300 indices (about 3x for 1,000 in Phase B).

## Finding (fixed here): open scroll context limit
A scroll keeps one context per shard and slice. `--slices 2` over `many-*` needs 600 > ES's default
`search.max_open_scroll_context` (500); ES answers HTTP 500 "Trying to create too many scroll contexts". Before
this commit the tool retried it 5 times (about 20 s) and, after L-804b, exited 4 (transient) with only the raw
body. A rerun of the same dump hits the same limit, so now it is not retried, exits 1, and the message names
the setting, `--slices`, dumping fewer indices per run, and the point-in-time dump (which opens no scroll
contexts; the PIT probe of `many-*` passes). For Phase B: a one-slice scroll over 1,000 single-shard indices
already needs 1,000 contexts, so it needs PIT or a raised limit.
Tests: unit `exit_code_tests` (500 scroll limit -> 1), chaos `l809_scroll_context_limit_fails_once_with_a_hint`.
