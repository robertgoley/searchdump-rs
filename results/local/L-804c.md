# L-804c: CI `it` jobs fixed after L-804b (lost context exits 4)

## Finding
Since L-804b (7e6b7e6) every `it` job on `main` failed (run 43650706812: elasticsearch-plain, es710-plain,
opensearch-plain, opensearch-secure; each 89 passed, 1 failed). The one failure on all four was
`chaos::l618_lost_search_context_names_the_keep_alive_flag` at tests/it/chaos.rs:145: it still expected exit 1,
but L-804b made a lost scroll or point-in-time context transient and rerun-safe (exit 4).

The local gate for L-804b, L-809, L-810 and L-812 ran tests/it with a bare `cargo test` against one ES 8.19 node
and compared it with a list of "14 known failures". That list was wrong: 13 of the 14 came from running the
suite without a profile (`IT_PROFILE`/`IT_ENGINE` unset, so OpenSearch-only tests ran against Elasticsearch),
and the 14th was this real regression. From now on the IT gate is `scripts/it/run.sh <profile>`.

## Fix
- tests/it/chaos.rs l618: both the scroll and the PIT part expect exit 4; the scroll message must still name
  `--scrollTime`, and now also the point-in-time way out and `--restartOnContextLoss`.
- src/retrieval/retrieval_task.rs: the scroll "context no longer exists" error (expired, index deleted, node
  restarted) now carries the same hint as the failed-continuation error from L-804b P4 (`--searchAfter --pit`,
  `--restartOnContextLoss N`). It did not before, so P4 covered only one of the two scroll-loss paths.
- Other exit-code assertions in tests/it checked: l619 already accepts 4 for a lost scroll context; the rest are
  permanent failures (mapping, auth, data streams, limits) that stay 1.
