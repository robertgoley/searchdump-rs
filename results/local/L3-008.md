# L3-008: searchdump-multi parent: retry read-only calls on HTTP 429/503 (bug found in 1.3-D runs)

Found in `results/load/l3-os3-exp-none` (OpenSearch 3.9.0, 256m, `--serverLimits=auto`, L3-004 build = 1.2.0
behaviour): `load-pmc` **exit 1** although the child wrote all 20,000 documents. The parent's
`POST /pmc/_refresh` (before its count check) got
`429 circuit_breaking_exception: [parent] Data too large, data for [<http_request>] would be [255751504/243.9mb],
which is larger than the limit of [255013683/243.1mb], real usage: [255751504/243.9mb], new bytes reserved: [0/0b]`
- a 0-byte request refused because the real heap usage alone was over the parent limit (garbage not yet
collected). `Cluster::call` sent every parent request exactly once (same in 1.1.0, `47a73cc` line 1344), so a
transient breaker answer failed the index. Not seen in the relcmp data, but the same code path exists in 1.1.0
and 1.2.0.

Fix (`src/bin/searchdump-multi.rs`): `Cluster::call` repeats a request answered with 429 or 503 up to
`PARENT_429_RETRIES` = 6 times (0.25 s doubling, max 4 s, ~12 s total), only for read-only calls (`GET`, `HEAD`,
`POST .../_refresh`, `POST .../_count`); it prints a `note:` line per retry. Index creation, deletes, bulks and
everything else are unchanged. Unit test `parent_retries_only_read_only_calls_on_429_and_503`.

For Robert: this changes behaviour only on a path that today fails the run (exit 1 for an index that was
fully written); proposed for 1.3 as a bug fix.
