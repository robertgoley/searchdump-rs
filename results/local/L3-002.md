Same case order, same flags, fresh engine: no mid-pass slowdown, metadata calls stay at 11-48 ms, no
restore stall. Together with L3-001 (interleaved A/B: 1.00-1.02x; identical request traces) the 1.3-G
slowdown is **not reproducible as a 1.2.0 property**. The kvmsvr1 pass `12` engine slowed down by itself
from ~05:55 ET (cheap metadata requests +30-650 ms each). Cause on that host not identifiable from the
committed data (no engine-side timings, no `_cat/pending_tasks`, no hot threads). A 1.1.0 pass on grokbox
for the same-host ratio is running (L3-003).

Note: kvmsvr1 is ~3x slower than grokbox on every OS3 restore (restore-none 12.1 s vs 3.9 s) in all
releases, so I/O on that host is the first suspect for both the pass-12 slowdown and the cross-release
~17 s / ~44 s restore stalls (also in 1.1.0: os3-secure multi-restore-p8 17.07 s; os2-secure, os3-secure,
os3-plain multi-restore-p1 44-46 s single reps). None seen on grokbox so far.

## 2. Harness (1.3-R1 review items 1-2): DELETE is awaited and logged

`scripts/perf/suite.py` `EngineRun.delete_index`: every target DELETE before a rep (`create_target`,
multi-restore `perf-dst-*`) now checks `acknowledged`, polls `GET /<index>/_settings` until 404 (bounded by
`PERF_DELETE_WAIT_S`, default 60 s; raises if not applied), and appends one line per DELETE (time, response,
acknowledged, gone, polls, wait) to `<result dir>/deletes.log`. The `finally` cleanup DELETE stays
best-effort. Selftests: updated `test_settings_target_is_left_absent`, new
`test_delete_index_waits_until_gone_and_logs`; `python3 scripts/perf/selftest.py`: 32 tests OK.
