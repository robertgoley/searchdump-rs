# L3-011: 1.3-D+ / 1.3-C / 1.3-E: why 1.2 small-heap OpenSearch 3 loads are slow, and the candidate fixes

grokbox, `scripts/load/lowheap.py` (pmc 20,000 x ~22 KB, fat 3,000 x ~78 KB; one shard, `dynamic: false`),
OpenSearch 3.9.0 / 2 / ES 9.1.2 at 256m and 384m, release assets for 1.1.0/1.2.0, `bin/l3exp*` = local builds
(L3-004 = 1.2 + 429 cause in the warning; L3-006 = + `retryfirst`; c205454 = + L3-008 parent retry).
Raw: `results/local/L3-011/lowheap/*.json` (one file per run id `l3-*`), kept child logs were in
`/var/tmp/searchdump-load/l3-*` (box only). Tables from `scripts/load/lowheap_cmp.py`; `split×N→K KB` = N bulk
splits, smallest cap K; `retry×N` = whole-request retries ("retrying in"); `cb` = the cause named
`circuit_breaking_exception`.

## 1. Root cause

Every 1.2 split on OS3 names the same cause (L3-004 logging), e.g.
`circuit_breaking_exception: [parent] Data too large, data for [<http_request>] would be [268815592/256.3mb], which
is larger than the limit of [255013683/243.1mb], real usage: [255731936/243.8mb]`. The **real heap usage alone**
is at or above the parent limit (uncollected garbage after the seed/dump); the request's own size (a few MB) is
not the problem. 1.1.0 retries the same request after its back-off; a GC has run by then and it goes through.
1.2.0 (L2-003) treats every breaker 429 as "too big", halves the bulk and **never grows back**: 3-7 splits per
load take the cap from 6.4-16 MB to 54-390 KB for the rest of the run (~25-100x more requests). This happens with
`--serverLimits=off` too (same 16 MB bulks as 1.1), so it is the 429 policy, not the `auto` sizing.
`retries=0` in the relcmp report: a split logs no "retrying in" line and (in 1.2.0) no error body, so lowheap
counted only the word "429" (and `cb=0`).

OS 2 and ES 9.1.2 at the same heaps: no splits at all in any run (`l3-os2es912-*`).

The page-budget-0 case (relcmp os3/384m dump-fat, 94 % heap) is the same effect on the dump side: the probe
read the full heap of garbage as "used". Not reproduced on grokbox (the dumps here probed 48-78 % used); the
`floor`/`configured` unit test (L3-003) reproduces the numbers from the probe line.

## 4. Reading

- 1.2.0 is 3.5x slower than 1.1.0 here (median 16.7 vs 4.7 s); every slow run has 3-5 splits.
- `retryfirst` removes the splits (0.0/run) and `growback` removes the "rest of the run" penalty; together they
  bring the median to 6.7 s (1.4x of 1.1.0). `floor` matters only for the dump-after-load probe (no dump here).
- `configured` sizing gave no load benefit in the single runs (it sizes larger, and the trips are real-memory
  trips); keep it only as an alternative to `floor` for the probe side.
- n=4 per variant on one host: the direction is consistent, the exact ratios are not precise.

## 5. Proposals for Robert (nothing changed by default)

1. **Decide 1.3 429 policy** (changes 1.2's L2-003 decision, so needs Robert): for a parent-breaker 429 whose
   `real usage` is already at/above the limit, resend once at the same size after the back-off before splitting
   (`retryfirst`), and let a split cap double again after 8 accepted bulks (`growback`). Measured best of the
   variants. Today both are opt-in via the hidden `SEARCHDUMP_LIMITS_EXPERIMENT=retryfirst,growback`.
2. **Decide the probe floor** (1.3-C/E): `floor` (never size from less than a quarter of the parent limit) so a
   probe right after a load cannot give a 0 MB page; or `configured` (half the configured limit). Opt-in today.
3. **Bug fix ready (L3-008)**: the multi parent now retries read-only calls on 429/503 (a 0-byte `_refresh` failed a
   fully written index at 256m). Proposed as a 1.3 fix.
4. Logging (L3-004): split/halve warnings now name the cause; lowheap should count `splitting it in half` /
   `halving the page` separately (lowheap_cmp.py does).
5. 1.3-C floor: OS 3 at 256m boots and passes every cell, but is the only engine that trips; keep 256m.
