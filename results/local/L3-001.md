# L3-001: 1.3-G first look - OpenSearch 3 plain, 1.1.0 vs 1.2.0 with identical flags

Box: grokbox (8 vCPU, 16 GB). Engine: OpenSearch 3.9.0 (images.lock digest `3b55f6b6...`), plain
(security plugin disabled, as `scripts/it/up.sh opensearch-plain`), 4096m heap, one engine for all reps.
Binaries: the published `x86_64-unknown-linux-gnu` release assets, sha256 verified against the release
`.sha256` files (searchdump 1.1.0 `ea7cec67...` is the same build as `/workspace/perf-1.2/bin-1.1.0`).

## 1. Interleaved A/B (scripts/perf/ab_os3g.py)

Same commands as Suite A (`--noDefaultDataFlags -- --limit=2000 --concurrency=1`, 16 x 6,250 docs for
multi), warm-up + 10 reps, the two binaries alternating A B / B A per rep on the same engine. All 132 runs
exit 0; restored indexes hold 6,250 docs each. Medians (s), `ab-os3-plain-4g.json`:

| case | 1.1.0 | 1.2.0 | 1.2/1.1 |
|---|---:|---:|---:|
| mapping-dump | 0.011 | 0.010 | 0.91 |
| mapping-restore | 0.018 | 0.019 | 1.02 |
| settings-dump | 0.009 | 0.009 | 1.08 |
| settings-restore | 0.039 | 0.039 | 1.01 |
| multi-dump-p8 | 0.149 | 0.150 | 1.00 |
| multi-restore-p8 | 0.771 | 0.776 | 1.01 |

No 1.2 slowdown when the engine state is shared.

## 2. Request traces (scripts/perf/trace_proxy.py)

multi-dump-p8 + settings-restore + multi-restore-p8 through a logging proxy, per release
(`trace-1.1.0.tsv`, `trace-1.2.0.tsv`; method, path, query, status, ms, sizes; no bodies or headers).
**The request sets are identical**: 17x `GET /`, 16x `GET /IDX/_settings`, 32x `_count`, 16 scroll opens,
64 scroll pages, 16 scroll clears, 64 `_bulk`, 32 `_refresh`, 1 `_cat/indices`, 1 `PUT /IDX`. With
`--noDefaultDataFlags` 1.2.0 sends no `_nodes/stats`, `_cluster/settings` or `_stats` call (plan_sizes
skips the probe and the stats call; children get `--serverLimits=off`). Metadata runs (`--type=mapping`,
`--type=settings`) never reach the 1.2 sizing code (`server_limits` returns before probing). So a bisect
over L2-003/004/005 has nothing to find for these cases; it was not run.

## 3. What the kvmsvr1 numbers say

Per-case 1.2/1.1 median ratios across all 16 engines (relcmp-20261117 suite-a): every engine is within
0.8-1.3 on mapping/settings/multi cases except **os3-plain**, where mapping-dump 2.11, mapping-restore
2.96, settings-dump 1.96, settings-restore 3.87, multi-dump-p8 3.99, multi-restore-p8 3.39.
The 1.2 code path for mapping/settings is unchanged from 1.1, yet those cases slowed by 30-650 ms per
request; in pass `12` the slowdown starts with mapping-dump at 05:55 ET (~14 min into the pass; earlier
data dumps/restores are 0.9-1.2x). multi-dump-p8's warm-up was normal (0.386 s) and the three reps after
it 1.35-1.38 s. That pattern (server-side latency on cheap requests, appearing mid-pass, one engine
instance only) points at the OpenSearch 3 plain engine of that pass (cluster-state / plugin background
work, e.g. query-insights `top_queries-*` index creation, which OS 3 does create on a plain node), not
at 1.2.0. Not yet proven: a full-sequence Suite A pass for os3-plain is being rerun on grokbox (L3-002).
